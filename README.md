# Task #4 — User Management (Ruby on Rails)

A business-oriented web application with **registration, authentication and a user
management table**, plus a **natural language assistant** that answers questions
about the data and **controls the dashboard**.

| | |
|---|---|
| Framework | Ruby 3.4+ / Rails 8.1 (`ruby 4.0.5` here) |
| Database | PostgreSQL 16 (Homebrew) |
| CSS framework | Bootstrap 5.3.3 + Bootstrap Icons 1.11.3 (served from the app itself) |
| Passwords | `has_secure_password` + bcrypt |
| Server | Puma, published over a Cloudflare TLS tunnel |
| Tests | 77 Minitest tests (263 assertions), a Postman collection (17 assertions), an acceptance test of the deployed application (21 checks), a browser check of the toolbar (14 checks) |

## 2. The design

The interface is built with **Bootstrap 5.3** and a **design system of design
tokens** — the whole look of the application can be changed by editing one
file.

```
app/assets/stylesheets/
├── bootstrap.min.css           the CSS framework
├── theme/
│   ├── tokens.css              THE TOKENS - the palette, the shapes, the type
│   ├── bootstrap-theme.css      the mapping of the tokens onto Bootstrap
│   └── components.css          the components of the application
└── application.css             the rules of the pages
```

* a **light and a dark theme** — the button in the navigation header (and on
  the sign in page) switches it; the choice is stored in a cookie and the
  **server renders the page in the chosen theme**, therefore there is no flash
  of the wrong theme while the page loads;
* the **sign in page** is a split screen: the form on the left, a geometric
  panel (pure CSS, no image, no animation) on the right;
* the **table** stands on a plain surface — the task asks for no wallpaper
  under the table;
* **no animations**, **no browser alerts**, **tooltips** on every action,
  **status messages** as Bootstrap alerts.

The complete documentation of the design system (the tokens, the components,
the rules and the recipes for a new component) is in
[`docs/DESIGN_SYSTEM.md`](docs/DESIGN_SYSTEM.md).

## 3. How the requirements are implemented

### 2.1 The unique index in the database (requirement 1)

`db/migrate/20260101000001_create_users.rb` creates **real unique indexes** —
not application level checks:

```
Indexes:
    "users_pkey" PRIMARY KEY, btree (id)
    "index_users_on_email" UNIQUE, btree (email)
    "index_users_on_lower_email" UNIQUE, btree (lower(email::text))
```

* `index_users_on_email` — the primary guarantee. PostgreSQL rejects a second
  row with the same e-mail, no matter which process or service writes it.
* `index_users_on_lower_email` — defence in depth: even a row written by raw
  SQL or by a data loader that bypasses the model cannot create a second
  account with the same e-mail in a different spelling.
* `users_pkey` — the primary key (a primary key is **not** a unique index on a
  business column, so both exist).

The model normalises the e-mail (`downcase`) before saving, therefore the plain
index already behaves case-insensitively. `test/models/user_test.rb` proves the
guarantee with a raw `INSERT` that must raise `ActiveRecord::RecordNotUnique`,
and the registration form turns that database error into a friendly message
(`rescue ActiveRecord::RecordNotUnique`).

### 2.2 The table and the toolbar (requirement 2)

* The table is a real HTML table (`<table class="table table-hover align-middle">`)
  with a header row, a body, aligned columns, `text-nowrap` for the
  timestamps and a centred checkbox column. The columns are: **checkbox, name
  (with the designation below it), e-mail, status, last login, last activity** —
  the design follows the table example of the task
  (`docs/reference/table-example.png`): the status is a text with a small dot,
  a blocked account is dimmed and its name is struck through, the timestamps
  are relative times ("4 hours ago") with the exact time in the tooltip, and
  under the last activity there is the small **bar chart with the activity of
  the last 14 days** (`user_activities`, one query for the whole table).
* The **toolbar is a card header above the table** and it never disappears —
  only the state of its buttons changes (`disabled` when the selection does not
  allow the action):

  | Action | Control | Enabled when |
  |---|---|---|
  | Block | **button with text** | ≥ 1 selected and at least one of them is active |
  | Unblock | **icon only** (`bi-unlock`) | ≥ 1 selected and at least one of them is blocked |
  | Delete | **icon only** (`bi-trash`) | ≥ 1 selected |

* There is **not a single button, link or label inside a data row** — only the
  checkbox of the leftmost column. (Asserted in
  `test/integration/users_admin_test.rb`.)

### 2.3 The data is sorted (requirement 3)

The table is **always sorted**, by default by the last login time (the most
recent login first, accounts that never logged in at the bottom):

```sql
ORDER BY users.last_login_at DESC NULLS LAST, users.email ASC
```

Every column header is a link that toggles the sort (name, e-mail, last login,
last activity, status, registration date), the current sort is marked and the
footer of the card repeats the active order.

### 2.4 Multiple selection with checkboxes (requirement 4)

* The leftmost column holds a checkbox per row (`name="user_ids[]"`).
* The header cell contains **only a checkbox, without a label**; it selects or
  deselects all the rows and shows the *indeterminate* state when only a part
  of the rows is selected.
* The selection is the payload of one POST form; the three toolbar buttons
  submit that form to different endpoints via the HTML5 `formaction`
  attribute — therefore the buttons work without JavaScript.

### 2.5 The check before every request (requirement 5)

`ApplicationController#require_authenticated_user` runs **before every action**
of every controller, except the registration and the login:

```ruby
user = current_user                       # re-read from the database on EVERY request
return if user.nil?                       # the account was deleted  -> login page
return if user.blocked?                   # the account was blocked  -> login page
```

* The session is reset and the browser is redirected to the login form.
* Because the account is read from the database on every request, blocking or
  deleting a user takes effect on the **very next request** of that user — also
  in a second browser tab.
* The JSON API answers with `401` instead of a redirect (a machine client
  cannot follow a redirect to a login form).

### 2.6 The rest of the rules

| Rule | Implementation |
|---|---|
| Non-authenticated visitors see only the login / registration form | every other route is protected by the filter above |
| Any non-empty password (even one character) | `validates :password, length: { minimum: 1 }`, bcrypt hashing |
| Registration happens right away, with a message | `redirect_to login_path, notice: "Registration successful. …"` |
| A blocked user cannot sign in | the login form answers with an error message |
| A deleted user can register again | the row is deleted, the e-mail is free again |
| Every user may block/delete himself and everybody else | there is no role, the toolbar acts on the selection |
| Deleted users are deleted, not marked | `UserBulkAction` uses `delete_all` (hard delete) |
| `getUniqIdValue` | `app/helpers/application_helper.rb` — see below |
| A CSS framework is used | Bootstrap 5.3.3 + Bootstrap Icons, served from `app/assets` |
| Tooltips | Bootstrap tooltips on the toolbar, the checkboxes, the sort links and the form fields |
| Status messages | Bootstrap alerts rendered into the page — **never** a browser `alert()` |
| Error messages | inline field errors + a summary of all errors on the registration form |
| No animations | `* { transition: none !important; animation: none !important; }` in `application.css` |
| No wallpaper | a plain, solid background colour (`#f4f6f8`) |
| Works on desktop and mobile | Bootstrap grid, `table-responsive`, verified with a 390×844 viewport |

### 2.7 `getUniqIdValue`

```ruby
def getUniqIdValue(salt = "uniq")
  @get_uniq_id_values ||= {}
  key = salt.to_s
  @get_uniq_id_values[key] ||= "#{key.dasherize}-#{SecureRandom.hex(5)}"
end
```

* It returns a **unique DOM id** for every element that needs one — the
  targets of the Bootstrap tooltips, the `for` attribute of the labels and the
  `id` attribute of the inputs.
* The value is memoised per salt **inside one request**, therefore
  `label for="…"` and `input id="…"` always match, while two requests never
  produce the same id.
* The salt is the name of the field (`getUniqIdValue("login-email")`), so the
  developer never invents an id by hand — the CSS framework (Bootstrap) then
  matches label, input and tooltip automatically.

## 4. Part 2 — ask the data in natural language

> *"Add the capability to ask question about your data/users using natural
> language and get answers as text. … You need to implement some API for AI to
> call to get correct results (typical models cannot count)."*

### The architecture

```
question / command
        │
        ▼
  Assistant::Planner ──────────► plan (JSON, whitelisted by Assistant::PlanSchema)
        │                           │
        │                           ▼
        │                   Assistant::Executor
        │                           │  HTTP (the own API of the application!)
        │                           ▼
        │                   GET /api/v1/users
        │                   GET /api/v1/users/stats
        │                           │  the numbers are computed by PostgreSQL
        │                           ▼
        └─────────────────► Assistant::AnswerFormatter ──► the answer as text
```

**The language model never produces a number.** The model (optional) only
translates the sentence into a *plan*; the plan is validated against a
whitelist, executed against the REST API of the application, and the answer is
assembled from the JSON the API returned. That is why the assistant cannot
hallucinate a count.

### The REST API (the contract)

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/users` | the users with filters (`q`, `email_prefix`, `email_contains`, `name_contains`, `domain`, `status`, `window`), sorting and paging |
| `GET /api/v1/users/stats` | every counter (`totals`, `overall`, `activity`, `groups`) — computed in SQL |
| `POST /api/v1/users/bulk_block` / `bulk_unblock` / `bulk_delete` | the toolbar actions |
| `POST /api/v1/assistant/ask` | a question → the answer as text |
| `POST /api/v1/assistant/command` | a command → the answer + the actions for the browser |

Authentication: the cookie of the signed in browser **or**
`Authorization: Bearer <token>` for server to server calls (the assistant uses
the token, it is derived from `secret_key_base`).

The full contract is described in [`openapi/openapi.yaml`](openapi/openapi.yaml)
and is executable as a Postman collection (see section 5).

### The planner

* `Assistant::RulePlanner` — a deterministic grammar (no key, no network, always
  available): intents, filters, sort and direction are extracted from the
  sentence.
* `Assistant::LlmPlanner` — optional. If `LLM_API_KEY` is set, a model
  (OpenAI or Anthropic) translates the sentence into the same plan with a
  strict JSON schema. If the model fails, the grammar takes over.

```bash
# optional: use a real language model for the translation
export LLM_PROVIDER=openai        # or anthropic
export LLM_API_KEY=…
export LLM_MODEL=gpt-4o-mini
```

### Examples (the answers come from the database)

| Question | Answer |
|---|---|
| `How many users are blocked?` | `109 blocked users in the system (226 users in total).` |
| `How many users logged in during the last 7 days?` | `11 users logged in during the last 7 days (226 users in total).` |
| `How many users registered this week?` | `226 users registered during the last 7 days (226 users in total).` |
| `How many users have never logged in?` | `… users have never logged in (226 users in total).` |
| `How many users are there per e-mail domain?` | `Users in the system - example.com: …, test: …` |
| `Show the users whose e-mail starts with s` | `Found … users with e-mail starting with s: sam@example.com, …` |
| `what is the status of sarah@gmail.com?` | `Sarah Smith (sarah@gmail.com) - status: active, last login: …` |

## 5. Part 3 — the bot controls the dashboard

> *"Make AI-bot able to control your dashboard or application, to do the
> commands like 'select users with e-mails started with s or p'."*

The assistant card above the table accepts a **command**. The answer contains
`ui_actions`, the browser applies them:

| Command | What happens |
|---|---|
| `select users with e-mails started with s or p` | the checkboxes of exactly these rows are ticked |
| `select the blocked users` | the checkboxes of the blocked rows are ticked |
| `clear the selection` | the selection is cleared |
| `sort by e-mail` | the table is sorted (no reload of the page) |
| `show only blocked users` | the filter of the table is changed |
| `block the selected users` | the API blocks the selection, the table is reloaded |
| `unblock the selected users` | the API unblocks the selection |
| `delete the selected users` | the API deletes the rows **physically** |
| `refresh the table` | the table is reloaded |

Destructive commands are executed by the **server** through the API (with the
service token), never by the browser, and the answer states how many users
were affected. The result of every command is shown as a status message inside
the page, and the plan plus the API calls can be opened below the answer
(*"Show the API calls and the plan"*).

## 6. The tests

```bash
bin/rails test          # 77 tests, 263 assertions
```

> The **CSRF protection is enabled in the test environment** — the tests send
> the token of the page, exactly like the browser does it. That is how the
> bug below was found: the toolbar of the table is ONE form that is submitted
> to THREE different endpoints (the HTML attribute `formaction` of the
> buttons), and the "per form" CSRF tokens of Rails are bound to the action of
> the form. They are switched off in `config/application.rb`, so the token of
> the session is valid for every action of the session.

| File | What it proves |
|---|---|
| `test/models/user_test.rb` | e-mail normalisation, the unique index (even against raw SQL), a one character password |
| `test/models/user_activity_test.rb` | the history of the activity: the recording, the throttle and the counters of the chart |
| `test/integration/authentication_test.rb` | registration, login, blocked / deleted users are sent back to the login page, a deleted user can register again |
| `test/integration/users_admin_test.rb` | the table, the toolbar, the sorting, the selection, **no button in a row**, block / unblock / delete, self block / self delete |
| `test/integration/api_test.rb` | the JSON API, the filters, the counters, the service token |
| `test/integration/assistant_test.rb` | the questions and the commands of the assistant |

> The table shows **all** the users of the current filter — there is no paging,
> so the checkbox in the header really selects *all* the records.

## 8. Notes

* **The database is the guarantee.** The application code only produces the
  friendly messages; the uniqueness of the e-mail is enforced by PostgreSQL.
* **The assistant never counts.** It asks the API, the API asks the database.
* **Everything is local.** Bootstrap, the icons and the fonts are served by the
  application itself — the panel also works without an internet connection.
* The Rails process listens on `127.0.0.1` only; the public access is provided
  by the TLS tunnel of `bin/tunnel`.
